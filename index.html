No database yet?

If your site needs to store things like sign-ups, messages or bookings, use this prompt so it's set up safely from the start.

Prompt for adding a database 
I need to add a database to my startup's website.

What the site does: [short description]
What I need to store: [e.g. contact form messages, user accounts, bookings]
Who should be able to see it: [e.g. only me as admin / each user only their own data]
Current setup: [e.g. static site on GitHub Pages, Next.js, WordPress]

Set it up securely:
- Recommend a simple option that fits my setup and explain why
- Only store what I listed, nothing extra
- Access rules from day one: nobody can read or change data unless they're allowed to
- If you use Supabase or Firebase, turn on Row Level Security / security rules for every table and write the policies
- Secret keys only on the server or in environment variables, never in the website's code
- Check data on the server before saving it
- Limit how often the form can be submitted, to stop spam

Explain the setup step by step, assuming I haven't done this before.
At the end, tell me how to test that a stranger can't read the data.
Prompt for building with security in mind 
My startup: [what it does]
Users: [who logs in, what they can do]
Tech: [e.g. PHP + MySQL, Next.js + Supabase]

Build this secure by default:
- Every page and API route checks the user is allowed to access that specific record, not just that they're logged in
- Users can't change fields like role, price or owner through the request
- Admin routes are checked on the server
- Supabase/Firebase: Row Level Security or security rules on every table, limited to the owner
- Rate-limit login and password reset
- Reset links expire and are single-use
- Sessions expire; cookies HttpOnly, Secure, SameSite
- Validate input on the server, escape output, parameterised queries
- CSRF protection on state-changing requests
- File uploads: allow-listed types, size limit, stored outside the web root
- Secrets only in environment variables, never in client code or Git
- Only use well-known, maintained packages

When done, list every remaining security risk and what I need to configure before launch.
Prompt for reviewing existing code 
Review this code as a security reviewer before it goes to production.

Focus on:
- Broken access control (can a user read or change another user's records?)
- Authentication and session handling
- Exposed secrets or keys
- Input validation, output escaping, injection
- CSRF on state-changing requests
- Database permissions / row-level rules
- Outdated or unknown dependencies

For each finding: explain the risk, rate it high/medium/low, and give the fix. Don't conclude it's secure unless every point was checked.
